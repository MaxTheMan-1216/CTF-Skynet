# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Terminator/Skynet-themed CTF site. Pure static HTML/CSS/JS — no framework, no dependencies, no build step, no tests.

The `NODES` array in `scripts/console.js` holds real flavor text and real answers for a 7-node main chain plus one bonus node, each keyed to an actual cipher (Caesar/ROT shift, Morse-coded audio, hex bytes, a flag-semaphore clock cipher, Vigenère, a Polybius square, Atbash, and a final key assembled from earlier answers). Don't treat that content as disposable placeholder text to freely rewrite — check with the user before changing puzzle answers, ciphers, or narrative body text. `n.answer` comparisons being client-side-only and the dev-only reset button (see below) are the actual "not production-ready yet" surfaces.

## Running it

Any static file server works, e.g.:

```bash
python -m http.server 8000
```

Opening the files directly (file://) also works. To skip the landing gate during development, open console.html directly; the gate's access phrase is `no fate` (`ACCESS_PHRASE` in `scripts/gate.js`). The phrase is also planted as a findable hint inside `index.html` itself (an HTML comment near the bottom) — the intended discovery path is "view page source," not the JS file.

## Architecture

Two pages, each with its own CSS/JS file, sharing one token stylesheet and a `scripts/`/`styles/` split:

- **index.html** + **styles/gate.css** + **scripts/gate.js** — landing gate. Boot animation plus an access-phrase form; the correct phrase redirects to console.html. The check is client-side only and is an extension point for a future real puzzle.
- **console.html** + **styles/console.css** + **scripts/console.js** — the "infiltration console" (nodes page). The map background is an inline SVG skull (`#skull-art`, viewBox `1600×1557`, traced centerline `<path>` strokes with a `stroke-dashoffset` draw-on reveal) — this is the confirmed final visual direction, not a placeholder; don't replace or "simplify" it. Game nodes render as `#ball-<id>` groups positioned directly in that same 1600×1557 coordinate space (see the `MAP_W`/`MAP_H` constants and the `NODES` array at the top of `scripts/console.js`), plus a mobile step-list fallback (<640px) and a briefing panel. A node's `status` (`cleared`/`current`/`locked`/`bonus`) drives styling, interactivity, and briefing content. `BONUS_ROUTES` (id pairs) draws the one dashed optional-branch line; there's no general `ROUTES` array — connectivity between the main nodes reads from the skull artwork's own line-art, not from drawn edges.
- **styles/theme.css** — design tokens (CSS custom properties: `--void`, `--signal`, `--phosphor`, …) and two fonts embedded as base64 data URIs. **Do not read this file whole** — it is almost entirely font data; the tokens are in the final ~25 lines (grep for `:root`).
- The inline skull SVG markup itself stays directly in `console.html` (not pulled into its own file) — CSS/JS reference it by id (`#skull-art`, `#ball-<id>`) and it needs to be real DOM, not a fetched asset. Pulling it out would also break `file://` (no-server) usage, see below.
- **audio/** — eight clips referenced by `<audio>` elements: `Landing-Intro.mp3`/`access_granted.mp3` for the gate (index.html); `TM-Intro.mp3` (console ambient loop), `Cleared.mp3` (per-node solve chime), `EE.wav` (one-shot deco-node discovery chime, `#deco-audio` — see `DECO_NODES` below) and `ending-typing.mp3` (typewriter-sound loop under the shutdown/ending sequence, `#ending-typing-audio`, started/stopped by `playShutdown()`) for console.html's own `<audio>` tags; plus `Node02_Signal.wav` and `Ending_Credits.mp3` used as puzzle/ending payloads from JS rather than static markup.

### Puzzle/progress system (scripts/console.js)

- `NODES` is the single source of truth for puzzle content (id, position, status, `answerHash`, flavor `body`, optional `cipher`/`meta`). `CHAIN` is the main-chain solve order (`clearNode()` walks it to unlock the next node); `BONUS_ROUTES` is `[from, to]` pairs unlocking the side-branch node (`b1`) without joining the main chain — always derive "is this node part of the main sequence" from `BONUS_ROUTES`' targets (see `buildList`'s comment), not a hand-maintained flag, or it drifts out of sync the way an earlier `n.bonus` field once did.
- Answers are never stored as plaintext, on purpose — `NODES[].answerHash` is a SHA-256 hash of `normalizeAnswer()`'s output, not the flag itself, specifically so opening dev tools / view-source doesn't hand a player the solution. `normalizeAnswer()` still does the actual leniency work (case/whitespace-insensitive, optional `flag{...}` wrapper, punctuation stripped, hyphens/underscores/spaces all treated as the same separator) — its output gets hashed via `sha256Hex()` and compared to `answerHash`, rather than compared as a string. `sha256Hex()` is a hand-written, from-spec SHA-256 (not `crypto.subtle.digest`) specifically because `crypto.subtle` only works in a secure context (https/localhost) and throws on `file://`, which would break local dev; it's synchronous for the same reason. If you ever need to regenerate a hash (e.g. an answer changes), don't hand-type it — compute it (e.g. `python3 -c "import hashlib; print(hashlib.sha256('normalized answer text'.encode()).hexdigest())"`) and verify the game still solves before committing, the same way this was verified when it was introduced. There's no plaintext canonical answer anywhere to fall back to for display either — a cleared node with no recorded `submittedAnswer` (e.g. a legacy save) shows "(not recorded)" instead, not the flag.
- `SKYNET_ENDING.flagCipher` (the final victory flag) can't be handled the same way as the node answers — hashing is one-way and this value has to actually be *displayed* once earned, not just checked. Instead it's XOR-encrypted against a keystream derived from `sha256Hex()` of n1-n7's own `submittedAnswer`s (`deriveEndingKey()`/`expandKeystream()`/`decryptEndingFlag()`, all in scripts/console.js near `sha256Hex`) — the same "key assembled from earlier answers" idea CORE's own in-fiction cipher already uses, just load-bearing this time. Reading the source gets you ciphertext and the algorithm, never the key, since the key only exists once a player has legitimately solved the main chain (`decryptEndingFlag()` returns a "(unavailable...)" message rather than garbage if any of n1-n7's `submittedAnswer` is missing, e.g. an old save). Regenerating `flagCipher` after changing the ending flag or any of n1-n7's answers needs the same care as regenerating an `answerHash` — derive it from the real `deriveEndingKey()`/`expandKeystream()` output, don't hand-type it, and round-trip it through `decryptEndingFlag()` before committing.
- Progress persists to **localStorage**, not sessionStorage (survives closing the tab): `skynet:progress` (per-node status/unlocked/submittedAnswer, restored by `loadProgress()` before first render) and `skynet:deco-found` (which decorative easter-egg nodes — see below — have been clicked). Both are wrapped in try/catch so private-browsing/quota failures just mean "progress doesn't persist," never a crash.
- `DECO_NODES` (`#ball-d1`..`d4`) are 4 pure-decoration ring icons baked into the skull artwork — clicking one replays the green clear-draw animation, plays a one-shot discovery chime (`EE.wav` via `#deco-audio`), and updates no briefing or counter. That chime is deliberately *not* routed through `duckAmbientFor()` the way puzzle clips are: it's a secret aside, not a puzzle beat, so ambient music keeps playing underneath it. Deliberately excluded from `NODES`/`CHAIN` and from keyboard handling (mouse-only secret, no hover affordance).
- `duckAmbientFor(mediaEl)` is the shared pattern behind "ambient music ducks under any puzzle clip or the solve chime": it wires `play`/`pause`/`ended` on a given `<audio>` to hold/release ambient via a counter (`duckedBy`, not a boolean, so overlapping clips can't release ambient early). Every puzzle audio player (`buildAudioPlayer`) and the cleared-chime element both go through it — don't gate ambient on `audioEl.paused` directly, that flag also flips during ducking and isn't a reliable read of user intent (`audioOn` is). Puzzle players are rebuilt fresh (a new `<audio>`, a fresh `duckAmbientFor` registration) on every `renderBriefing()` call, so `renderBriefing()` explicitly `.pause()`s whatever `<audio>` is still in the outgoing briefing before wiping it with `innerHTML = ""` — removing a *playing* media element from the DOM doesn't stop it (that's standard browser behavior, not a bug), and an orphaned-but-playing clip both keeps making sound and never fires the `pause`/`ended` event `duckAmbientFor` is waiting on to release its ambient duck, which is what "ambient randomly stays ducked or comes back at a weird moment" turned out to be. Any future code that swaps out a container holding a live `<audio>` needs the same explicit `.pause()` first — it's not something `duckAmbientFor` can protect against on its own, since by the time the element's gone, there's nothing left to call `.pause()` on.
- The `#reset-progress` button (console.html) + its console.js handler + `.hud-reset` CSS rules are an explicitly temporary dev/testing aid — clears `skynet:progress` and reloads. Flagged in all three files for removal before launch; don't extend it into a real feature without checking that's still wanted.

## Conventions the pages follow

- Each page's CSS lives in `styles/<page>.css`, JS in `scripts/<page>.js`, loaded via `<link rel="stylesheet">` / `<script src>` at the same point in the markup the inline block used to occupy (so load-order/timing is unchanged from when they were inline). Only shared tokens/fonts live in `theme.css`. Files start at `<title>` with no doctype/html/head/body wrappers — match that style. The one exception is the skull SVG markup in `console.html`, which stays inline (see Architecture above).
- Audio and entry animations are gated behind the first click/keypress (browser autoplay policy). Both pages use a run-once flag plus a `.play` class that the CSS animation blocks key off.
- Every animation has a `prefers-reduced-motion` story: entry/looping animations live inside `no-preference` media blocks so reduced-motion users get the final state immediately (nothing is left at `opacity: 0` waiting on an animation that never runs).
- Staggered reveals use a per-item `--i` custom property set from JS, consumed by `animation-delay: calc(var(--i) * Xms)`.
- Colors always come from the theme tokens: `--signal` (red) is the accent/danger color, `--cleared` the green for done states.
