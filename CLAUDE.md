# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Terminator/Skynet-themed CTF site, live at **skynet-ctf.org**, deployed as a Cloudflare **Worker with static assets** — not classic Cloudflare Pages, an easy assumption to make wrong (see the caution below, this repo already did once). The Cloudflare project (`ctf-skynet`) is connected via GitHub integration: its dashboard build config runs `npm ci && npm run build` then `npx wrangler deploy` on every push to `main`, reading `wrangler.toml` at the repo root. `src/index.js` is the actual Worker entry point — its `fetch()` handler intercepts `POST /check-answer` itself and falls through to Cloudflare's static-asset serving (the `ASSETS` binding) for literally everything else. The pages themselves still have no framework and no dependencies of their own to write — but as of 2026-08-15 there **is** a real build step for the deployed site specifically (`build/strip-comments.mjs`, generating `dist/`), requested explicitly to keep this repo's own extensive documentation comments out of what a player can view-source; see the **build/**, **package.json** entry below and its own top-of-file comment for the full reasoning. `src/index.js`/`wrangler.toml`/`build/`/`package.json` are the parts of the repo that aren't themselves a static asset — `dist/` (gitignored, generated fresh on every build) is an *allowlist*, not the old `.assetsignore` exclude-list this replaced: only files `build/strip-comments.mjs` explicitly copies ever reach it, so a new non-public file added to the repo root is safe by default now rather than needing someone to remember to exclude it.

**Caution for future changes here:** an earlier version of this server-side answer-checking was built as a Cloudflare *Pages* Function (`functions/check-answer.js`, file-based routing, no `wrangler.toml` needed) — a reasonable-sounding default that turned out to be the wrong product for this specific deployment. Since this project has no `wrangler.toml` unless it's the one at the repo root, and `wrangler deploy` with none present silently falls back to "just serve this directory as static files" rather than erroring, that mismatch shipped silently: answer submission 404'd on the live site, and the Pages-Function file's own source (hashes included) got served as a plain public file instead of executed. If touching deploy config again, verify against the actual dashboard build settings (Settings → Build) rather than assuming which Cloudflare product is in play.

The `NODES` array in `scripts/console.js` holds real flavor text and real answers for a 7-node main chain plus one bonus node, each keyed to an actual cipher (Caesar/ROT shift, Morse-coded audio, hex bytes, a flag-semaphore clock cipher, Vigenère, a Polybius square, Atbash, and a final key assembled from earlier answers). Don't treat that content as disposable placeholder text to freely rewrite — check with the user before changing puzzle answers, ciphers, or narrative body text. Answer-checking used to be client-side-only (a real gap: view-source handed out both the hash and the exact algorithm to verify guesses against it, for free, no rate limit) — that moved server-side into `src/index.js` on 2026-08-15, see the Puzzle/progress system section below. The dev-only reset button (see below) is the one remaining "not production-ready yet" surface.

## Running it

Any static file server works, e.g.:

```bash
python -m http.server 8000
```

Opening the files directly (file://) also works. To skip the landing gate during development, open console.html directly; the gate's access phrase is `no fate` (`ACCESS_PHRASE` in `scripts/gate.js`). The phrase is also planted as a findable hint inside `index.html` itself (an HTML comment near the bottom) — the intended discovery path is "view page source," not the JS file. Note that `POST /check-answer` (see Architecture below) needs the deployed Worker or a local `wrangler dev`/`wrangler pages dev` session to respond — it 404s under a plain static server or `file://`, so answer submission specifically won't work locally without one of those, even though everything else does.

**Something to know before editing anything here:** this repo has, at least at times, had local tooling that auto-commits and auto-pushes file changes to `main` in something close to real time — discovered 2026-08-15 when edits made in a session turned up on GitHub, and then live on skynet-ctf.org, without anyone running `git commit`/`git push` or a deploy command directly. If that's still active, there is no review/staging gap between "edit a file here" and "it's live in production" — normal caution about testing before committing doesn't provide the safety net it would in a repo where commits are deliberate. Verify with the user whether this is still happening before assuming an edit is safely uncommitted.

## Architecture

Two pages, each with its own CSS/JS file, sharing one token stylesheet and a `scripts/`/`styles/` split:

- **index.html** + **styles/gate.css** + **scripts/gate.js** — landing gate. Boot animation plus an access-phrase form; the correct phrase redirects to console.html. The check is client-side only and is an extension point for a future real puzzle.
- **console.html** + **styles/console.css** + **scripts/console.js** — the "infiltration console" (nodes page). The map background is an inline SVG skull (`#skull-art`, viewBox `1600×1557`, traced centerline `<path>` strokes with a `stroke-dashoffset` draw-on reveal) — this is the confirmed final visual direction, not a placeholder; don't replace or "simplify" it. Game nodes render as `#ball-<id>` groups positioned directly in that same 1600×1557 coordinate space (see the `MAP_W`/`MAP_H` constants and the `NODES` array in `scripts/console.js` — deliberately not positioned at the very top of that file, see its own Puzzle/progress system note on file layout below), plus a mobile step-list fallback (<640px) and a briefing panel. A node's `status` (`cleared`/`current`/`locked`/`bonus`) drives styling, interactivity, and briefing content. `BONUS_ROUTES` (id pairs) draws the one dashed optional-branch line; there's no general `ROUTES` array — connectivity between the main nodes reads from the skull artwork's own line-art, not from drawn edges.
- **styles/theme.css** — design tokens (CSS custom properties: `--void`, `--signal`, `--phosphor`, …) and two fonts embedded as base64 data URIs. **Do not read this file whole** — it is almost entirely font data; the tokens are in the final ~25 lines (grep for `:root`).
- The inline skull SVG markup itself stays directly in `console.html` (not pulled into its own file) — CSS/JS reference it by id (`#skull-art`, `#ball-<id>`) and it needs to be real DOM, not a fetched asset. Pulling it out would also break `file://` (no-server) usage, see below.
- **audio/** — eight clips referenced by `<audio>` elements: `Landing-Intro.mp3`/`access_granted.mp3` for the gate (index.html); `TM-Intro.mp3` (console ambient loop), `Cleared.mp3` (per-node solve chime), `EE.wav` (one-shot deco-node discovery chime, `#deco-audio` — see `DECO_NODES` below) and `ending-typing.mp3` (typewriter-sound loop under the shutdown/ending sequence, `#ending-typing-audio`, started/stopped by `playShutdown()`) for console.html's own `<audio>` tags; plus `Node02_Signal.wav` and `Ending_Credits.mp3` used as puzzle/ending payloads from JS rather than static markup.
- **wrangler.toml** + **src/index.js** — the live Worker, see the Project section above for the deploy mechanics. `src/index.js`'s `fetch()` handler does node-answer checking server-side for `POST /check-answer` (holds the only copy of each node's `answerHash` — `NODES[]` in console.js has none anymore) and falls through to `env.ASSETS.fetch(request)` for everything else, which serves whatever `npm run build` most recently generated into `dist/`. `scripts/console.js` sends `{nodeId, guess}` to `CHECK_ENDPOINT` (`/check-answer`, a relative path — same Worker serves both, so no CORS needed) and gets back `{correct}`, nothing else. Rate limiting is a per-IP counter via a `RATE_LIMIT` KV binding declared in `wrangler.toml`'s `kv_namespaces` (real namespace id, `ctf-rate-limit`) — has to stay above `[assets]` in that file, not below: TOML scopes every key after a `[table]` header into that table, so a `kv_namespaces` placed after `[assets]` silently becomes `assets.kv_namespaces` instead of top-level (caught once already by validating the parsed file, not by eye — worth the same care if this section is edited again). `src/index.js` still fails safe if that binding is ever missing (answer-checking works, just without rate limiting, rather than every guess erroring) — relevant if this project is ever cloned/redeployed under a fresh KV setup.
- **build/strip-comments.mjs** + **package.json** (repo root, npm deps `terser`/`clean-css`) — generates `dist/`, what `[assets].directory` in `wrangler.toml` actually points at (not `.` / repo root anymore). Two jobs, both requested explicitly on 2026-08-15, not a default worth applying without being asked: strips comments from the shipped JS/CSS/HTML (this repo's comments are written for maintainers, not players — several, especially the red-herring ones just below, would spoil their own joke if a curious player could read the "this is fake" explanation sitting right next to the fake thing), and copies only an explicit allowlist of files at all (`index.html`, `console.html`, `styles/*`, `scripts/*`, `audio/*` — see `HTML_FILES`/`JS_FILES`/`CSS_FILES`/`COPY_DIRS` in the script). JS goes through `terser` and CSS through `clean-css` rather than hand-rolled regex specifically because both parse real syntax instead of pattern-matching text — a regex can't reliably tell a real comment from a `//` inside a string or (concretely, for `styles/theme.css`'s ~66KB of base64 font data) a coincidental `/*`-shaped byte sequence inside an otherwise-unrelated blob; verified byte-identical after stripping, not just "didn't error", before trusting this. `KEEP_HTML_COMMENTS` in the script is an explicit allowlist of intentional in-fiction comments (the real access-phrase hint, the red herrings) that survive stripping by literal substring match — anything not on that list gets removed, no exceptions. This is a real, deliberate departure from "no build step" for the deployed artifact specifically; the repo's own source files stay exactly as commented as ever, `dist/` is gitignored and regenerated fresh on every Cloudflare build (`npm ci && npm run build`, configured in the dashboard's Settings → Build, not in any committed config file), and reverting after the CTF ends is just pointing `[assets].directory` back at `.` and clearing that dashboard field.
- **Red herrings (scripts/console.js, index.html, console.html), added 2026-08-15:** intentionally misleading content for whoever reads source out of curiosity — a `DEBUG_SKIP_CHECK` constant referenced nowhere in real logic, a pool of console.log taunts in CORE's voice logged on every `console.html` load, a fake "leaked bypass phrase" HTML comment, and three small solvable ciphers (ROT13/hex/Atbash — the Atbash one deliberately parked next to the real ending-flag markup, since Atbash is also b1's real bonus-answer cipher) that decode to jokes, not flags. Ground rule that must hold for any future addition here: red herrings live entirely in decorative/comment/console-log space, **never** in a real code path — nothing decorative gets wired into actual answer-checking or progress logic. Rely on `build/strip-comments.mjs`'s `KEEP_HTML_COMMENTS` allowlist (see above) to keep the HTML ones visible post-build while every self-explaining "this is fake" comment gets stripped same as any other comment — don't weaken that explanation in the source thinking it needs to be subtle there too, the build step is what handles hiding it from players, not the wording.

### Puzzle/progress system (scripts/console.js)

- **File layout is deliberate, not incidental (2026-08-15):** the file opens with the generic crypto/encoding utilities (`normalizeAnswer`, `utf8Encode`/`Decode`, `sha256Hex`, `hexToBytes`/`bytesToHex`, `expandKeystream`, `deriveEndingKey`, `decryptEndingFlag`, `scrambleText`, `statusLabel`) — `NODES`/`CHAIN`/`BONUS_ROUTES`/`SKYNET_ENDING` (the actual puzzle content) sit further in, not at the top. Requested explicitly: opening the file shouldn't immediately hand a casual source-reader the flavor text/cipher values before they've scrolled past something boring. This is a mild deterrent, not a real barrier — it only affects the raw committed source; the actually-deployed site strips comments and serves from `dist/` regardless (see the **build/** entry below). If reordering this file again, avoid comments that assert a position ("near the top of this file", "above", "below") across a section that might move independently later — several went stale during this exact reorder and had to be found by grep, not by eye. Reference by name instead ("see X's own comment") wherever the two things being cross-referenced aren't guaranteed to stay adjacent.
- **A `const` declared right before the function that reads it is not automatically safe (found and fixed 2026-08-15+):** `settleShutdown()` and `playShutdown()` are both defined well down the file, so a shared constant seemed natural to declare immediately above them. But `settleShutdown()` has a call site *earlier* in the script's own top-to-bottom execution — the boot-time "returning player whose save already has CORE cleared" restore check, which runs during initial page load, long before the script reaches that constant's own declaration line. The function itself is hoisted and callable from anywhere (it's a function declaration), but a `const`/`let` it references is in the temporal dead zone until its own line actually executes — so calling the function from that earlier point threw `ReferenceError: Cannot access '...' before initialization`, aborting the *entire rest of the script*, including the press-any-key listener registration near the end of the file. Symptom looked totally unrelated to the cause: "press any key doesn't do anything," reproducible only for a returning already-won player, invisible for a fresh one. Fix was moving the constant up next to `SKYNET_ENDING` (already safely before every call site). If adding another constant shared by both shutdown paths, declare it that early too — not next to whichever of the two functions happens to read it first in the file.
- `NODES` is the single source of truth for puzzle content (id, position, status, flavor `body`, optional `cipher`/`meta`) — no `answerHash` field anymore, see below. `CHAIN` is the main-chain solve order (`clearNode()` walks it to unlock the next node); `BONUS_ROUTES` is `[from, to]` pairs unlocking the side-branch node (`b1`) without joining the main chain — always derive "is this node part of the main sequence" from `BONUS_ROUTES`' targets (see `buildList`'s comment), not a hand-maintained flag, or it drifts out of sync the way an earlier `n.bonus` field once did.
- Answer-checking happens server-side, in `src/index.js` (the live Worker — see the **wrangler.toml + src/index.js** entry in Architecture above). `scripts/console.js`'s flag-submit handler is `async`: it `fetch()`s `CHECK_ENDPOINT` with `{nodeId, guess}` and gets back `{correct: true|false}`, nothing else — no hash, no algorithm, ever ships to the browser for this anymore. This replaced an earlier client-side-only design (`NODES[].answerHash` + a local `sha256Hex(normalizeAnswer(guess)) === answerHash` compare) that had a real gap: reading source handed out the hash *and* the exact check to run against it, so anyone could brute-force-verify candidate guesses locally, for free, with no rate limit and without ever using the site's own submit button. `src/index.js` holds the only copy of each `answerHash` now and enforces a real per-IP rate limit (via a Cloudflare KV binding) — something that structurally cannot be done in code the player controls. Because the same Worker serves both the API route and the static files, it needs no CORS/preflight handling at all. `normalizeAnswer()` (still in console.js) is applied to a guess *before* it's sent — `src/index.js` re-applies the identical rules server-side before hashing, so the two copies of that function must stay byte-for-byte identical, or a guess accepted on one side gets rejected on the other. If a node's answer ever changes, regenerate its hash the same careful way as before (don't hand-type it — compute it and verify) and update `ANSWER_HASHES` in `src/index.js`, then push — there's nothing left to update in `scripts/console.js` for that specific field. There's still no plaintext canonical answer anywhere in the static site to fall back to for display — a cleared node with no recorded `submittedAnswer` (e.g. a legacy save) shows "(not recorded)" instead, not the flag; that part is unchanged, since `submittedAnswer` is just whatever the *player* typed, recorded client-side the moment `src/index.js` confirms it correct, not derived from a hash.
- `sha256Hex()` (hand-written, from-spec SHA-256, not `crypto.subtle.digest`, specifically because `crypto.subtle` throws outside a secure context and would break `file://` local dev) is still in console.js — it no longer does node-answer checking, but `deriveEndingKey()`/`expandKeystream()`/`decryptEndingFlag()` (the ending-flag XOR mechanism, unchanged, see below) still need it, so don't remove it thinking it's dead code. It's a coincidence worth knowing about, not a design dependency, that `src/index.js`'s own hashing uses the real `crypto.subtle.digest` instead (see the comment on `sha256Hex()` in that file) — a Worker always runs in a secure server context, so it never hit the constraint that made the hand-rolled version necessary client-side in the first place.
- `SKYNET_ENDING.flagCipher` (the final victory flag) can't be handled the same way as the node answers — hashing is one-way and this value has to actually be *displayed* once earned, not just checked. Instead it's XOR-encrypted against a keystream derived from `sha256Hex()` of n1-n7's own `submittedAnswer`s (`deriveEndingKey()`/`expandKeystream()`/`decryptEndingFlag()`, all in scripts/console.js near `sha256Hex`) — the same "key assembled from earlier answers" idea CORE's own in-fiction cipher already uses, just load-bearing this time. Reading the source gets you ciphertext and the algorithm, never the key, since the key only exists once a player has legitimately solved the main chain (`decryptEndingFlag()` returns a "(unavailable...)" message rather than garbage if any of n1-n7's `submittedAnswer` is missing, e.g. an old save). Regenerating `flagCipher` after changing the ending flag or any of n1-n7's answers needs the same care as regenerating an `answerHash` — derive it from the real `deriveEndingKey()`/`expandKeystream()` output, don't hand-type it, and round-trip it through `decryptEndingFlag()` before committing.
- Progress persists to **localStorage**, not sessionStorage (survives closing the tab): `skynet:progress` (per-node status/unlocked/submittedAnswer, restored by `loadProgress()` before first render), `skynet:deco-found` (which decorative easter-egg nodes — see below — have been clicked), `skynet:deco-bonus` (`DECO_BONUS_KEY`, the confirmed fragments-bonus reward text once earned — see the `DECO_NODES` bullet below), and `skynet:elapsed-seconds` (`ELAPSED_KEY`, the HUD's "Session T+" stat — accumulated *active* playtime in whole seconds, written every tick rather than only on unload so an ungraceful close loses at most a second of it, not the whole session; an earlier version tracked wall-clock time since first visit instead via a since-removed `skynet:session-start` key, replaced entirely, nothing migrates between the two). `#reset-progress` clears all four together, see below. All wrapped in try/catch so private-browsing/quota failures just mean "progress doesn't persist," never a crash.
- `DECO_NODES` (`#ball-d1`..`d4`) are 4 ring icons baked into the skull artwork — clicking one replays the green clear-draw animation and plays a one-shot discovery chime (`EE.wav` via `#deco-audio`; deliberately *not* routed through `duckAmbientFor()` the way puzzle clips are — it's a secret aside, not a puzzle beat, so ambient music keeps playing underneath it). Still deliberately excluded from `NODES`/`CHAIN` and from keyboard handling (mouse-only secret, no hover affordance), and a click itself still updates no briefing or counter — but as of 2026-08-15 each also carries a `fragment` string, and finding all 4 (`decoFound.length === DECO_NODES.length`) unlocks a real bonus level, not a passive reveal: a submission form appears in a new HUD-anchored panel (`#fragments-toggle`/`#fragments-panel`, hidden until all 4 are found — same "no advance affordance" principle as the deco hotspots themselves, carried further than an early version's "shows partial progress" behavior; nothing at all hints this exists until the whole set is already complete). The panel doesn't just ask for the fragments retyped — that was an earlier pass and wasn't really a puzzle, just a memory check. Now the 4 fragments, concatenated in `DECO_NODES`' own array order (order matters — a shuffled key decrypts to garbage), are the Vigenère key (`DECO_CIPHERTEXT`) for a shown ciphertext, the same mechanism NODE_05 already teaches; the decrypted plaintext (currently `"there are others"`, still draft) is what actually gets submitted, through the same lenient `normalizeAnswer()` every other answer gets. It's checked exactly like every other node's answer — `POST /check-answer` with `nodeId: "deco"` — **not** auto-derived client-side. An earlier version of this feature did derive the reward client-side (XOR-decrypted from a key built off `DECO_NODES[].fragment`) and that was a real flaw: those fragments are plain source strings, readable without ever finding a single deco, so nothing was actually protected. The fix: `src/index.js`'s `ANSWER_HASHES.deco` holds the hash same as any node, and a small `REWARDS` lookup there (opt-in per node id, so it changes nothing about n1-n7/b1's response shape) means a *correct* `"deco"` submission gets `{correct: true, reward: "..."}` back instead of the usual bare `{correct}` — the reward string never ships to the client at all until genuinely earned. Solving it (not just finding all 4 — `decoBonusReward !== null`, not `decoFound.length`) is what unlocks light-touch hints appended in `renderBriefing()` for NODE_04/NODE_05 specifically (the two hardest ciphers — confirms cipher family/key location, doesn't solve them). `DECO_BONUS_KEY` (`localStorage`) persists the confirmed reward text itself once earned, same "store the confirmed value, not just a boolean" approach `NODES[].submittedAnswer` already uses, so a reload shows the solved state without a second server round-trip. Closing the panel doesn't depend solely on re-clicking `#fragments-toggle` (on narrower layouts the open panel can render partially behind it, making that click unreachable) — `openFragmentsPanel()`/`closeFragmentsPanel()` centralize the state change so a `.fragments-close` button built into the panel's own content and a document-level click-outside listener both reach it too. `fragmentsPanelJustOpened` exists specifically so the very click that *opens* the panel (the toggle, or the completing 4th deco find) doesn't immediately bubble to that outside-click listener and close what it just opened — a one-frame flicker that's a known trap in "click outside to close" implementations generally, not specific to this one; worth remembering if another dismissible panel is ever added here.
- `duckAmbientFor(mediaEl)` is the shared pattern behind "ambient music ducks under any puzzle clip or the solve chime": it wires `play`/`pause`/`ended` on a given `<audio>` to hold/release ambient via a counter (`duckedBy`, not a boolean, so overlapping clips can't release ambient early). Every puzzle audio player (`buildAudioPlayer`) and the cleared-chime element both go through it — don't gate ambient on `audioEl.paused` directly, that flag also flips during ducking and isn't a reliable read of user intent (`audioOn` is). Puzzle players are rebuilt fresh (a new `<audio>`, a fresh `duckAmbientFor` registration) on every `renderBriefing()` call, so `renderBriefing()` explicitly `.pause()`s whatever `<audio>` is still in the outgoing briefing before wiping it with `innerHTML = ""` — removing a *playing* media element from the DOM doesn't stop it (that's standard browser behavior, not a bug), and an orphaned-but-playing clip both keeps making sound and never fires the `pause`/`ended` event `duckAmbientFor` is waiting on to release its ambient duck, which is what "ambient randomly stays ducked or comes back at a weird moment" turned out to be. Any future code that swaps out a container holding a live `<audio>` needs the same explicit `.pause()` first — it's not something `duckAmbientFor` can protect against on its own, since by the time the element's gone, there's nothing left to call `.pause()` on.
- The `#reset-progress` button (console.html) + its console.js handler + `.hud-reset` CSS rules are an explicitly temporary dev/testing aid — clears all four `localStorage` keys above and reloads. Flagged in all three files for removal before launch; don't extend it into a real feature without checking that's still wanted.

## Conventions the pages follow

- Each page's CSS lives in `styles/<page>.css`, JS in `scripts/<page>.js`, loaded via `<link rel="stylesheet">` / `<script src>` at the same point in the markup the inline block used to occupy (so load-order/timing is unchanged from when they were inline). Only shared tokens/fonts live in `theme.css`. Files start at `<title>` with no doctype/html/head/body wrappers — match that style. The one exception is the skull SVG markup in `console.html`, which stays inline (see Architecture above).
- Audio and entry animations are gated behind the first click/keypress (browser autoplay policy). Both pages use a run-once flag plus a `.play` class that the CSS animation blocks key off.
- Every animation has a `prefers-reduced-motion` story: entry/looping animations live inside `no-preference` media blocks so reduced-motion users get the final state immediately (nothing is left at `opacity: 0` waiting on an animation that never runs).
- Staggered reveals use a per-item `--i` custom property set from JS, consumed by `animation-delay: calc(var(--i) * Xms)`.
- Colors always come from the theme tokens: `--signal` (red) is the accent/danger color, `--cleared` the green for done states.
