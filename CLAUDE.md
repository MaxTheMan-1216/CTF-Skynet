# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Terminator/Skynet-themed CTF site, live at **skynet-ctf.org**, deployed as a Cloudflare **Worker with static assets** — not classic Cloudflare Pages. `src/index.js` is the Worker entry point: its `fetch()` handler intercepts eight `POST` API routes itself and falls through to `env.ASSETS.fetch(request)` (the static-asset binding) for everything else. The Cloudflare project (`ctf-skynet`) deploys via GitHub integration — Settings → Build runs `npm ci && npm run build` then `npx wrangler deploy` on every push to `main`.

**Caution:** an earlier version of the answer-checking was a Cloudflare *Pages* Function (`functions/check-answer.js`, file-based routing, no `wrangler.toml`). Since `wrangler deploy` with no `wrangler.toml` silently falls back to "serve this directory as static files" instead of erroring, that mismatch shipped silently — answer submission 404'd live, and the Pages-Function's own source got served as a plain public file. If touching deploy config, verify against the actual dashboard Build settings rather than assuming which Cloudflare product is in play.

There's a real build step for the *deployed* artifact only: `build/strip-comments.mjs` generates a gitignored `dist/`, which is what `wrangler.toml`'s `[assets].directory` actually points at. The repo's own source files stay fully commented; `dist/` strips them so players can't view-source the reasoning (several comments, especially red-herring ones, would spoil their own joke otherwise).

The `NODES` array in `scripts/console.js` holds real flavor text for a 7-node main chain plus one bonus node. **Puzzle answers, ciphers, and narrative body text are not disposable placeholder content — check with the user before changing any of it.**

**Before editing anything here:** this repo has, at times, had local tooling that auto-commits/auto-pushes to `main` in near real time (edits have turned up on GitHub and live on skynet-ctf.org without anyone running `git commit`/`git push`). Verify with the user whether that's currently active before assuming an edit is safely uncommitted — there may be no staging gap between "edit a file" and "it's in production."

## Commands

- **Local static preview** (no API routes): `python -m http.server 8000`, or just open the HTML files via `file://`. Good enough for everything except `/check-answer`, `/check-gate`, and the other API routes below, which 404 without a live Worker.
- **Full local dev (matches production):**
  ```
  npm install        # pulls in terser + clean-css, the only devDependencies
  npm run build       # generates dist/ — required first; dist/ is gitignored and wrangler.toml's [assets].directory points at it, not the repo root
  npx wrangler dev    # reads wrangler.toml, serves the Worker + dist/ together
  ```
  Not `wrangler pages dev` — that's the Pages product and won't read this project's `[assets]` config the same way.
- **No lint or test command** — `build` is the only script in `package.json`, and there's no test suite in the repo.
- Rebuilding (`npm run build`) while `wrangler dev` is already running can break its static-asset serving for a while afterward; restart `wrangler dev` if assets look stale.
- To skip the landing gate during dev, open `console.html` directly. The gate's access phrase is `no fate` (checked server-side, see below — not readable from client source).

## Architecture

### Pages

Two pages, no framework, each with its own CSS/JS, sharing one token stylesheet:

- **index.html** + **styles/gate.css** + **scripts/gate.js** — landing gate (boot animation, access-phrase form). `gate.js` holds no copy of the phrase — it POSTs a raw guess to `/check-gate`, which checks it against `GATE_ANSWER_HASH` in `src/index.js` and returns `{correct}`, nothing else.
- **console.html** + **styles/console.css** + **scripts/console.js** — the "infiltration console" / node map. The map background is an inline SVG skull (`#skull-art`, `viewBox="97 37 1518 1483"`, matching `console.js`'s `VIEW_X/VIEW_Y`/`MAP_W/MAP_H` constants) — traced centerline strokes with a `stroke-dashoffset` draw-on reveal. This is the confirmed final visual direction; don't replace or simplify it. Game nodes render as `#ball-<id>` groups positioned directly in that coordinate space (see the `NODES` array), plus a mobile step-list fallback (<640px) and a briefing panel. There's no general `ROUTES` array for connectivity between main nodes — that reads from the skull artwork's own line-art; `BONUS_ROUTES` only draws the one dashed optional-branch line.
- **styles/theme.css** — design tokens (`--void`, `--signal`, `--phosphor`, …) plus two fonts embedded as base64 data URIs. **Don't read this file whole** — it's almost entirely font data; tokens are in the final ~25 lines.
- The skull SVG markup stays inline in `console.html` (not a separate file) — it needs to be real DOM sized by the live page, and pulling it out would break `file://` (no-server) usage and hand a source-reader a trivially fetchable asset.
- **audio/** — clips referenced by `<audio>` tags: `Landing-Intro.mp3`/`access_granted.mp3` (gate), `TM-Intro.mp3` (console ambient loop), `Cleared.mp3` (solve chime), `EE.wav` (deco-node discovery chime), `ending-typing.mp3` (shutdown sequence). `Node02_Spectrogram.wav` is NODE_02's cipher payload but is fetched from the Worker (`/node-audio`, see below), not linked as a static asset. `Node02_Signal.wav` (an old Morse clip) and `Knock.mp3` are unreferenced by any code — orphaned, safe to ignore or remove.
- **mission-briefing.md** — in-fiction player-facing briefing text, not dev documentation.

### Worker (`src/index.js` + `wrangler.toml`)

`wrangler.toml`'s `name = "ctf-skynet"` must stay exactly that — wrangler uses it to identify which existing Worker to update, and it's what's bound to the skynet-ctf.org domain. Changing it deploys a brand-new, unbound Worker instead.

Routes eight `POST` endpoints, falls through to `env.ASSETS.fetch(request)` for everything else:

| Endpoint | Purpose | Rate limit (per IP/60s) |
|---|---|---|
| `/check-answer` | Node-answer checking — holds the only copy of each node's `answerHash` | 5 |
| `/reveal-glyph` | Hands back one letter of the day's glyph alphabet at a time | 60 |
| `/reveal-fragment` | Hands back one decorative-node fragment word at a time | 6 |
| `/node-cipher` | Hands back today's glyph-index array for a given node | 30 |
| `/node-audio` | Hands back NODE_02's cipher audio as raw `audio/wav` bytes | 10 |
| `/verify-turnstile` | Verifies a Turnstile token, mints a session token | 10 |
| `/check-gate` | index.html's access-phrase check (not a node) | 8 |
| `/gate-qr` | Hands back the QR module grid for the gate phrase's second hint channel (not a node) | 8 |

Buckets are independent (`RATE_LIMITS` in `src/index.js`) via a `RATE_LIMIT` KV binding declared in `wrangler.toml` — that `kv_namespaces` key must stay *above* `[assets]` in the TOML, since everything after a `[table]` header scopes into that table (a `kv_namespaces` below `[assets]` silently becomes `assets.kv_namespaces`). The Worker fails safe if `RATE_LIMIT` is missing (endpoints work, just unthrottled) rather than erroring — relevant if this is ever redeployed under a fresh KV setup. Same Worker serves the API and static files, so no CORS handling is needed.

**Session/Turnstile gate** — every endpoint above except `/verify-turnstile` and `/check-gate` requires a valid `X-Session-Token` header (`requireSession()`), closing raw-`curl`/API-only access that never executes page JS. `scripts/console.js`'s `acquireSessionToken()` renders an Invisible-mode Turnstile widget the first time a gated endpoint is needed; its callback posts the token to `/verify-turnstile`, which re-verifies against Cloudflare's `siteverify` and mints a session token (`base64url(payload) + "." + base64url(HMAC-SHA256)`, signed with `SESSION_SIGNING_SECRET`, 4h TTL). `apiFetch()` in console.js attaches the cached token to every gated call and retries once on a 401 (expired/invalid token) after re-acquiring. **This does not and cannot stop a genuine browser-automation agent that actually solves Turnstile** — it only closes headless API-only access, a deliberate scope call.
- Fails **open**, not closed, if `SESSION_SIGNING_SECRET` is unset (same fail-safe shape as the missing-KV case) — a missing secret just means the gate hasn't activated yet, not that the site breaks for players.
- `/check-gate` is deliberately *not* behind this gate — it's the front door, protecting one static phrase that never rotates; a rate limit alone is the proportionate friction there.
- `.dev.vars` (gitignored) holds Cloudflare's public Turnstile *test* sitekey/secret pair for local dev — production needs its own real sitekey (swapped into `TURNSTILE_SITE_KEY` in console.js) and freshly generated `SESSION_SIGNING_SECRET`/`TURNSTILE_SECRET_KEY` set via `wrangler secret put`, **before** pushing this code live, or the gate silently doesn't gate anything.
- Two non-obvious Turnstile integration facts, in case the widget is touched again: an Invisible-mode widget never executes if its container is `display: none` (no error at all) — position it off-screen instead (`position: absolute; left: -9999px`); and Turnstile's SDK throws if `async`/`defer` is combined with calling `turnstile.ready()` before `render()` — drop `async`/`defer` and call `render()` directly if the script tag's position already guarantees load order.

### Build pipeline (`build/strip-comments.mjs`)

Generates `dist/` from an explicit **allowlist** (not the old `.assetsignore` exclude-list) — only `index.html`, `console.html`, `styles/*`, `scripts/*`, `audio/*` (minus a few private files filtered by name) ever reach it, so a new file added to the repo root is safe-by-default. JS goes through `terser`, CSS through `clean-css` at `level: 1, specialComments: 0` (not `level: 0` — that leaves every comment byte-for-byte untouched, a real bug fixed once already) — both parse real syntax rather than regex-matching, which matters concretely for `theme.css`'s ~66KB of base64 font data that could coincidentally contain comment-shaped byte sequences. `KEEP_HTML_COMMENTS` in the script is an explicit allowlist of intentional in-fiction comments (red herrings) that survive stripping; everything else is removed, no exceptions. If this build step is ever touched, verify output is byte-identical apart from intended stripping (especially font data URIs) rather than assuming "didn't error" is sufficient.

### Puzzle/progress system (`scripts/console.js`)

- **File layout is deliberate**: the file opens with generic crypto/encoding utilities (`normalizeAnswer`, `sha256Hex`, `expandKeystream`, `deriveEndingKey`, `decryptEndingFlag`, `scrambleText`, …) before `NODES`/`CHAIN`/`BONUS_ROUTES`/`SKYNET_ENDING` (the actual puzzle content) — a mild deterrent against a casual source-reader immediately hitting flavor text/cipher values. Only affects raw committed source; the deployed site strips comments regardless.
- **Temporal-dead-zone trap, hit twice already**: a `const`/`let` declared right before the function that reads it isn't automatically safe if that function also has an *earlier* call site elsewhere in the script's top-to-bottom execution (e.g. a boot-time "returning player" restore check). The function itself is hoisted (safe from anywhere), but a `const` it closes over is not — calling in from an earlier point throws `ReferenceError: Cannot access '...' before initialization` and **aborts the entire rest of the script**, including listener registration near the end. Symptom looks unrelated to cause (e.g. "press any key does nothing," reproducible only for a specific save state). If adding a constant shared across code paths with different call-site timing, declare it as early as the earliest of those call sites needs, not next to whichever consumer happens to be nearby in the file.
- `NODES` is the single source of truth for puzzle content (id, position, status, flavor `body`, optional `cipher`/`meta`) — no `answerHash` field; those live only in `src/index.js`. `CHAIN` is the main-chain solve order; `BONUS_ROUTES` (`[from, to]` pairs) unlocks the side-branch node (`b1`) — always derive "is this node part of the main sequence" from `BONUS_ROUTES`' targets, not a hand-maintained flag.
- **Cipher chain**: n1 (ROT13, glyph-rendered), n2 (audio steganography — spectrogram of `Node02_Spectrogram.wav` spells out Atbash ciphertext, fetched via `/node-audio` rather than a static file), n3 (reversal, glyph-rendered), n4 (flag-semaphore clock cipher), n5 (Vigenère, keyed off n1's `meta` header digits, glyph-rendered as of 2026-08-19 — see `GLYPH_CIPHERTEXTS.n5` in `src/index.js`), n6 (Polybius grid, glyph-digit rendered), n7/CORE (XOR against a key derived from n1–n6's own answers, rendered in CORE's own glyph-hex dialect as of 2026-08-19 — see below), b1 (glyph + Vigenère(deco-bonus-reward) + Atbash, bonus). NODE_01's `meta` line is deliberately duplicated (with genuinely different digits, not identical text) across several nodes as a decoy — only n1's actually feeds n5's key.
- **`cipher.type: "glyph-hex"` (CORE/n7 only, added 2026-08-19)**: a third, distinct symbol dialect belonging only to CORE — fill *and* ticks together (`.glyph-hex-icon` in `styles/console.css`), a combination neither of the other two glyph treatments uses (the 26-letter alphabet is outline+ticks, NODE_06's digits are fill-only). Reuses `glyphMarkup()` unchanged, just called with indices 0–15 instead of 0–25, for one symbol per hex nibble — no new shape generator to maintain. Colored `--ember`/`--ember-glow` specifically, matching CORE's own already-established map identity, not `--signal` or `--flame`. Always shown (a hex nibble isn't a secret mapping the way a letter is, same reasoning NODE_06's digits already establish) — no reveal mechanic, no rotation, no server endpoint. `NODES[].n7.cipher.value` is an array of `[highNibble, lowNibble]` pairs, one per source byte — the exact same XOR ciphertext this node has always used, just restructured; regenerate by converting the hex string and round-tripping back to confirm an exact match before trusting it, same discipline as everything else here. **Deliberately fully manual** (transcribe every symbol by eye, same as n1/n3/n5), a large volume (69 bytes / 138 symbols) — a real UX tradeoff the user chose knowingly, not an oversight; if CORE's cipher is ever revisited, don't "fix" this into something more convenient without checking first.
- **Glyph cipher system** (`cipher.type: "glyph"`/`"glyph-grid"`, used by n1/n3/n6/b1/the deco bonus): a homebrew symbol alphabet — not a textbook cipher — specifically because textbook ciphers (Caesar, hex, Vigenère, etc.) pattern-match instantly to LLM-assisted solving. The index→letter mapping and every glyph node's ciphertext **rotate daily**, computed server-side from a salt + UTC date (`todayGlyphLetters()` in `src/index.js`) and never stored — this caps a leaked mapping's blast radius to ~24h, it does not slow down extraction happening today (rate limits are the delay for that, and even those only turn seconds into minutes for a scripted client). Consequences for editing this: `NODES[]` glyph entries carry `cipher.key` (looked up against `GLYPH_CIPHERTEXTS` in `src/index.js`), not a precomputed `cipher.value` array; `console.js` fetches `/node-cipher` fresh per render. A node's own encoded message is never independently clickable (only the 26-symbol reference key triggers `/reveal-glyph`), and a node's answer can't be submitted until every glyph in *that node's own message* has been revealed in the current render — a client-side speed bump, not a security boundary (it doesn't and can't stop a direct `POST /check-answer` with an already-known answer).
- **CORE (n7)'s key** is `JCRAIA` — derived from each of n1–n6's own `meta` "freq" decimal digit picking *which* letter of that node's answer counts toward the key (not always the first letter). b1's answer (`"ROOT KEY JCRAIA"`) hands this key to players who complete the separate deco-fragments bonus, as a shortcut. If any of n1–n6's answers or `meta` digits change, both CORE's `cipher.value` (XOR ciphertext in console.js) and b1's ciphertext/hash (in `src/index.js`) need regenerating — derive them from a real script, verify by round-tripping decrypt→matches-plaintext→matches-live-hash, don't hand-type.
- **Deco bonus**: `DECO_NODES` (`#ball-d1`..`d4`) are 4 mouse-only hotspots baked into the skull artwork, excluded from `NODES`/`CHAIN`/keyboard handling. Finding all 4 reveals a fragments panel; the 4 fragment words (held server-side in `DECO_FRAGMENTS`, revealed one at a time via `/reveal-fragment`) concatenate in array order into a Vigenère key decrypting a shown glyph ciphertext to `"there are others"`, submitted through the normal `/check-answer` flow (`nodeId: "deco"`) — not auto-derived client-side. A correct `deco` submission gets an opt-in `{reward, hints}` in the response (via `REWARDS`/`HINTS` in `src/index.js`), unlocking light-touch hints for NODE_04/NODE_05 in the briefing.
- **Ending flag** (`SKYNET_ENDING.flagCipher`) can't be hash-checked like node answers since it has to be displayed once earned — it's XOR-encrypted against a keystream derived from `sha256Hex()` of n1–n7's own `submittedAnswer`s (`deriveEndingKey()`/`expandKeystream()`/`decryptEndingFlag()`, all in console.js). Reading source gets ciphertext + algorithm, never the key, since the key only exists once a player has legitimately solved the main chain. Regenerating it after any answer change needs the same derive-and-round-trip discipline as everything else here.
- `sha256Hex()` in console.js is hand-written from spec (not `crypto.subtle.digest`) specifically because `crypto.subtle` throws outside a secure context and would break `file://` local dev — it no longer does answer-checking, but the ending-flag mechanism still needs it. `src/index.js` uses real `crypto.subtle.digest` (a Worker always runs in a secure context).
- **Progress persists to `localStorage`** (survives tab close, not just session): `skynet:progress`, `skynet:deco-found`, `skynet:deco-bonus`, `skynet:elapsed-seconds`, `skynet:deco-fragments`, `skynet:deco-hints`, plus an in-memory-only (not persisted) `glyphRevealedByKey` map for glyph reveal state, which does reset on a full page reload by design. `#reset-progress` (console.html) clears all the `localStorage` keys and reloads — an explicitly temporary dev/testing aid, flagged for removal before launch.
- **Red herrings** (`scripts/console.js`, `index.html`, `console.html`): a `DEBUG_SKIP_CHECK` constant referenced nowhere real, CORE-voice console.log taunts, a fake "leaked bypass phrase" comment, and small solvable ROT13/hex/Atbash ciphers that decode to jokes, not flags. **Ground rule for any future addition**: red herrings live entirely in decorative/comment/console-log space — never wired into real answer-checking or progress logic.
- `duckAmbientFor(mediaEl)` is the shared pattern for "ambient music ducks under any puzzle clip or the solve chime" — uses a counter, not a boolean, so overlapping clips can't release the duck early. Any code that removes a container holding a live `<audio>` must explicitly `.pause()` it first — removing a playing element from the DOM doesn't stop playback or fire the `pause`/`ended` event this pattern waits on.

### Hidden gate hint (`index.html` + `styles/gate.css` + `scripts/gate.js`)

A near-invisible QR code is the **sole** discovery channel for the gate phrase as of 2026-08-19 (an earlier letterform-SVG hint that lived alongside it was removed at the user's request — see git history if that mechanism is ever wanted back). `index.html` has only an empty `<div class="hidden-signal-qr">`; `gate.js` fetches the module grid from `POST /gate-qr` and builds the SVG at runtime. This split is load-bearing, not stylistic: unlike traced letterform paths (which need real rendering + visual recognition before they mean anything to a source-reader), a QR module grid **is** the fully-decoded payload the instant it's read — shipping it as static markup would hand the phrase to any QR-decoding script pointed at source, no color trick required. `GATE_QR_MODULES` in `src/index.js` is static (doesn't rotate, matching the phrase itself) and only rate-limited (`gateQr` bucket, same tier as `gate` — not session-gated), a deliberate proportionality call consistent with `/check-gate`'s own: this is the front door, not real puzzle content, and a scripted caller can extract the raw module data directly (no rendering needed) with nothing but the rate limit as friction. If the gate phrase ever changes, regenerate this matrix (via the `qrcode` npm package, not a project dependency) and re-verify with a **real** decoder before replacing the constant — see why below.

Fill is a +1 achromatic delta over `--void` (`#090a0b`), same small-size/no-hue-mismatch reasoning as this project's other near-invisible elements. `.gate-screen { position: relative }` is still required — zero visual effect on its own, but necessary to keep `.hidden-signal-qr` (position:fixed, no z-index) from landing in the wrong paint layer given `html`/`body` both set a background in `theme.css`; removing it reintroduces a real occlusion bug hit once already on the old letterform hint.

**A real, non-obvious bug found 2026-08-19, worth understanding fully before touching this again: QR polarity.** A QR decoder requires standard polarity — dark modules = low reflectance, light modules = high. But this page's background is already close to the darkest a pixel can be, so the near-invisible signal this technique relies on can only ever render *brighter* than background, never darker. The first implementation drew the **dark** modules as that brighter signal — which produces an image that looks like a valid QR and is even still recoverable-looking, but is fully polarity-inverted from what any standards-compliant decoder expects. The fix (`gate.js`): draw the near-invisible fill on **light** modules and the entire quiet zone, and leave dark modules undrawn (showing the page's true, unmodified background) — so a normal boost (low→black, high→white) resolves to correct polarity automatically.

This shipped and passed testing initially because validation used `jsQR`, a lenient pure-JS library that tolerates inverted input — false confidence. Swapping to `zbar` (the library many real-world scanner apps are actually built on) failed on the exact same image `jsQR` had called successful, and continued failing across a fill-delta sweep from +1 to +20, lossless or through JPEG — ruling out contrast entirely and pointing at something structural. **Lesson for any future recoverable-hidden-content work in this repo: validate against a real, independent decoder implementation, not just one library, before trusting a "successful" automated test** — the same category of mistake as trusting a screenshot glance instead of pixel data, just one level removed.

**Also fixed the same day, both real and independently necessary:**
- **Quiet zone**: QR standard requires a plain margin (≥4 modules) around the code before any real scanner will even *locate* it, not just decode it correctly — added at render time in `gate.js` (not baked into `GATE_QR_MODULES`, which stays exactly what the `qrcode` library produces) via a `QUIET_ZONE` constant offsetting drawn coordinates.
- **No `blur()`** on this element, unlike what might be assumed from the letterform hint's own history — blur helped there (softens edges for a human eye) but actively hurts here (a QR decoder locates modules by sharp edges; blur smears exactly that boundary information on top of an already-tiny delta).
- Fill-delta magnitude turned out **not** to be the sensitive variable once polarity was fixed — a delta as small as +1 decodes reliably through a full JPEG round-trip with correct polarity. Don't assume a bigger delta buys QR scan reliability; re-verify with a real decoder if this is ever revisited rather than assuming.

**Recovery in general needs a real contrast-stretch/auto-levels operation, not a linear brightness slider** — a plain multiply clips background and signal to the same value before their ratio ever separates. The red-herring ROT13'd comment near the bottom of `index.html` is unrelated to any of this — a separate, untouched decoy.

## Operational notes

- `pkill -f "wrangler dev"` does not reliably kill the real server — it matches wrapper-layer command lines (`npm exec`/`sh -c`) but not the actual long-lived process (`wrangler-dist/cli.js dev` or the `workerd` binary), leaving orphaned processes on incrementing ports. Kill by literal PID instead: `pgrep -af "wrangler|workerd"`, kill every matching PID, confirm the port is clear (`ss -tlnp`) before relaunching.

## Conventions the pages follow

- Each page's CSS lives in `styles/<page>.css`, JS in `scripts/<page>.js`, loaded at the same point in the markup the inline block used to occupy. Only shared tokens/fonts live in `theme.css`. Files start at `<title>` with no doctype/html/head/body wrappers — match that style (the skull SVG in `console.html` is the one intentional exception, kept inline).
- Audio and entry animations are gated behind the first click/keypress (browser autoplay policy) via a run-once flag plus a `.play` class the CSS animation keys off.
- Every animation has a `prefers-reduced-motion` story: entry/looping animations live inside `no-preference` media blocks so reduced-motion users get the final state immediately.
- Staggered reveals use a per-item `--i` custom property set from JS, consumed by `animation-delay: calc(var(--i) * Xms)`.
- Colors always come from theme tokens: `--signal` (red) is the accent/danger color, `--cleared` the green for done states.
