# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Terminator/Skynet-themed CTF site, live at **skynet-ctf.org**, deployed as a Cloudflare **Worker with static assets** — not classic Cloudflare Pages, an easy assumption to make wrong (see the caution below, this repo already did once). The Cloudflare project (`ctf-skynet`) is connected via GitHub integration: its dashboard build config runs `npx wrangler deploy` on every push to `main`, reading `wrangler.toml` at the repo root. `src/index.js` is the actual Worker entry point — its `fetch()` handler intercepts `POST /check-answer` itself and falls through to Cloudflare's static-asset serving (the `ASSETS` binding) for literally everything else, so the static pages below still have no framework, no dependencies, and no build step of their own; `src/index.js` and `wrangler.toml` are the one part of the repo that isn't a static asset, and `.assetsignore` (repo root) is what keeps them — and anything else non-public — from being served as one.

**Caution for future changes here:** an earlier version of this server-side answer-checking was built as a Cloudflare *Pages* Function (`functions/check-answer.js`, file-based routing, no `wrangler.toml` needed) — a reasonable-sounding default that turned out to be the wrong product for this specific deployment. Since this project has no `wrangler.toml` unless it's the one at the repo root, and `wrangler deploy` with none present silently falls back to "just serve this directory as static files" rather than erroring, that mismatch shipped silently: answer submission 404'd on the live site, and the Pages-Function file's own source (hashes included) got served as a plain public file instead of executed. If touching deploy config again, verify against the actual dashboard build settings (Settings → Build) rather than assuming which Cloudflare product is in play.

The `NODES` array in `scripts/console.js` holds real flavor text and real answers for a 7-node main chain plus one bonus node, each keyed to an actual cipher (Caesar/ROT shift, Morse-coded audio, hex bytes, a flag-semaphore clock cipher, Vigenère, a Polybius square, Atbash, and a final key assembled from earlier answers). Don't treat that content as disposable placeholder text to freely rewrite — check with the user before changing puzzle answers, ciphers, or narrative body text. Answer-checking used to be client-side-only (a real gap: view-source handed out both the hash and the exact algorithm to verify guesses against it, for free, no rate limit) — that moved server-side into `src/index.js` on 2026-08-15, see the Puzzle/progress system section below. The dev-only reset button (see below) is the one remaining "not production-ready yet" surface.

## Running it

Any static file server works, e.g.:

```bash
python -m http.server 8000
```

Opening the files directly (file://) also works. To skip the landing gate during development, open console.html directly; the gate's access phrase is `no fate` (`ACCESS_PHRASE` in `scripts/gate.js`). The phrase is also planted as a findable hint inside `index.html` itself (an HTML comment near the bottom) — the intended discovery path is "view page source," not the JS file. Note that `POST /check-answer` (see Architecture below) needs the deployed Worker or a local `wrangler dev`/`wrangler pages dev` session to respond — it 404s under a plain static server or `file://`, so answer submission specifically won't work locally without one of those, even though everything else does.

**Something to know before editing anything here:** this repo has, at least at times, had local tooling that auto-commits and auto-pushes file changes to `main` in something close to real time — discovered 2026-08-15 when edits made in a session turned up on GitHub, and then live on skynet-ctf.org, without anyone running `git commit`/`git push` or a deploy command directly. If that's still active, there is no review/staging gap between "edit a file here" and "it's live in production" — normal caution about testing before committing doesn't provide the safety net it would in a repo where commits are deliberate. Verify with the user whether this is still happening before assuming an edit is safely uncommitted.

## Architecture

Two pages, each with its own CSS/JS file, sharing one token stylesheet and a `scripts/`/`styles/` split:

- **index.html** + **styles/gate.css** + **scripts/gate.js** — landing gate. Boot animation plus an access-phrase form; the correct phrase redirects to console.html. The check is client-side only and is an extension point for a future real puzzle.
- **console.html** + **styles/console.css** + **scripts/console.js** — the "infiltration console" (nodes page). The map background is an inline SVG skull (`#skull-art`, viewBox `1600×1557`, traced centerline `<path>` strokes with a `stroke-dashoffset` draw-on reveal) — this is the confirmed final visual direction, not a placeholder; don't replace or "simplify" it. Game nodes render as `#ball-<id>` groups positioned directly in that same 1600×1557 coordinate space (see the `MAP_W`/`MAP_H` constants and the `NODES` array at the top of `scripts/console.js`), plus a mobile step-list fallback (<640px) and a briefing panel. A node's `status` (`cleared`/`current`/`locked`/`bonus`) drives styling, interactivity, and briefing content. `BONUS_ROUTES` (id pairs) draws the one dashed optional-branch line; there's no general `ROUTES` array — connectivity between the main nodes reads from the skull artwork's own line-art, not from drawn edges.
- **styles/theme.css** — design tokens (CSS custom properties: `--void`, `--signal`, `--phosphor`, …) and two fonts embedded as base64 data URIs. **Do not read this file whole** — it is almost entirely font data; the tokens are in the final ~25 lines (grep for `:root`).
- The inline skull SVG markup itself stays directly in `console.html` (not pulled into its own file) — CSS/JS reference it by id (`#skull-art`, `#ball-<id>`) and it needs to be real DOM, not a fetched asset. Pulling it out would also break `file://` (no-server) usage, see below.
- **audio/** — eight clips referenced by `<audio>` elements: `Landing-Intro.mp3`/`access_granted.mp3` for the gate (index.html); `TM-Intro.mp3` (console ambient loop), `Cleared.mp3` (per-node solve chime), `EE.wav` (one-shot deco-node discovery chime, `#deco-audio` — see `DECO_NODES` below) and `ending-typing.mp3` (typewriter-sound loop under the shutdown/ending sequence, `#ending-typing-audio`, started/stopped by `playShutdown()`) for console.html's own `<audio>` tags; plus `Node02_Signal.wav` and `Ending_Credits.mp3` used as puzzle/ending payloads from JS rather than static markup.
- **wrangler.toml** + **src/index.js** + **.assetsignore** — the live Worker, see the Project section above for the deploy mechanics. `src/index.js`'s `fetch()` handler does node-answer checking server-side for `POST /check-answer` (holds the only copy of each node's `answerHash` — `NODES[]` in console.js has none anymore) and falls through to `env.ASSETS.fetch(request)` for everything else, which is what actually serves index.html/console.html/styles/scripts/audio. `scripts/console.js` sends `{nodeId, guess}` to `CHECK_ENDPOINT` (`/check-answer`, a relative path — same Worker serves both, so no CORS needed) and gets back `{correct}`, nothing else. Rate limiting is a per-IP counter via a `RATE_LIMIT` KV binding declared in `wrangler.toml`'s `kv_namespaces` (real namespace id, `ctf-rate-limit`) — has to stay above `[assets]` in that file, not below: TOML scopes every key after a `[table]` header into that table, so a `kv_namespaces` placed after `[assets]` silently becomes `assets.kv_namespaces` instead of top-level (caught once already by validating the parsed file, not by eye — worth the same care if this section is edited again). `src/index.js` still fails safe if that binding is ever missing (answer-checking works, just without rate limiting, rather than every guess erroring) — relevant if this project is ever cloned/redeployed under a fresh KV setup. `.assetsignore` excludes `src/`, `wrangler.toml`, and other non-public files from what `[assets]` can ever serve — anything not listed there is a publicly fetchable file on skynet-ctf.org the moment it's deployed, so add new non-public files there too.

### Puzzle/progress system (scripts/console.js)

- `NODES` is the single source of truth for puzzle content (id, position, status, flavor `body`, optional `cipher`/`meta`) — no `answerHash` field anymore, see below. `CHAIN` is the main-chain solve order (`clearNode()` walks it to unlock the next node); `BONUS_ROUTES` is `[from, to]` pairs unlocking the side-branch node (`b1`) without joining the main chain — always derive "is this node part of the main sequence" from `BONUS_ROUTES`' targets (see `buildList`'s comment), not a hand-maintained flag, or it drifts out of sync the way an earlier `n.bonus` field once did.
- Answer-checking happens server-side, in `src/index.js` (the live Worker — see the **wrangler.toml + src/index.js + .assetsignore** entry in Architecture above). `scripts/console.js`'s flag-submit handler is `async`: it `fetch()`s `CHECK_ENDPOINT` with `{nodeId, guess}` and gets back `{correct: true|false}`, nothing else — no hash, no algorithm, ever ships to the browser for this anymore. This replaced an earlier client-side-only design (`NODES[].answerHash` + a local `sha256Hex(normalizeAnswer(guess)) === answerHash` compare) that had a real gap: reading source handed out the hash *and* the exact check to run against it, so anyone could brute-force-verify candidate guesses locally, for free, with no rate limit and without ever using the site's own submit button. `src/index.js` holds the only copy of each `answerHash` now and enforces a real per-IP rate limit (via a Cloudflare KV binding) — something that structurally cannot be done in code the player controls. Because the same Worker serves both the API route and the static files, it needs no CORS/preflight handling at all. `normalizeAnswer()` (still in console.js) is applied to a guess *before* it's sent — `src/index.js` re-applies the identical rules server-side before hashing, so the two copies of that function must stay byte-for-byte identical, or a guess accepted on one side gets rejected on the other. If a node's answer ever changes, regenerate its hash the same careful way as before (don't hand-type it — compute it and verify) and update `ANSWER_HASHES` in `src/index.js`, then push — there's nothing left to update in `scripts/console.js` for that specific field. There's still no plaintext canonical answer anywhere in the static site to fall back to for display — a cleared node with no recorded `submittedAnswer` (e.g. a legacy save) shows "(not recorded)" instead, not the flag; that part is unchanged, since `submittedAnswer` is just whatever the *player* typed, recorded client-side the moment `src/index.js` confirms it correct, not derived from a hash.
- `sha256Hex()` (hand-written, from-spec SHA-256, not `crypto.subtle.digest`, specifically because `crypto.subtle` throws outside a secure context and would break `file://` local dev) is still in console.js — it no longer does node-answer checking, but `deriveEndingKey()`/`expandKeystream()`/`decryptEndingFlag()` (the ending-flag XOR mechanism, unchanged, see below) still need it, so don't remove it thinking it's dead code. It's a coincidence worth knowing about, not a design dependency, that `src/index.js`'s own hashing uses the real `crypto.subtle.digest` instead (see the comment on `sha256Hex()` in that file) — a Worker always runs in a secure server context, so it never hit the constraint that made the hand-rolled version necessary client-side in the first place.
- `SKYNET_ENDING.flagCipher` (the final victory flag) can't be handled the same way as the node answers — hashing is one-way and this value has to actually be *displayed* once earned, not just checked. Instead it's XOR-encrypted against a keystream derived from `sha256Hex()` of n1-n7's own `submittedAnswer`s (`deriveEndingKey()`/`expandKeystream()`/`decryptEndingFlag()`, all in scripts/console.js near `sha256Hex`) — the same "key assembled from earlier answers" idea CORE's own in-fiction cipher already uses, just load-bearing this time. Reading the source gets you ciphertext and the algorithm, never the key, since the key only exists once a player has legitimately solved the main chain (`decryptEndingFlag()` returns a "(unavailable...)" message rather than garbage if any of n1-n7's `submittedAnswer` is missing, e.g. an old save). Regenerating `flagCipher` after changing the ending flag or any of n1-n7's answers needs the same care as regenerating an `answerHash` — derive it from the real `deriveEndingKey()`/`expandKeystream()` output, don't hand-type it, and round-trip it through `decryptEndingFlag()` before committing.
- Progress persists to **localStorage**, not sessionStorage (survives closing the tab): `skynet:progress` (per-node status/unlocked/submittedAnswer, restored by `loadProgress()` before first render) and `skynet:deco-found` (which decorative easter-egg nodes — see below — have been clicked). Both are wrapped in try/catch so private-browsing/quota failures just mean "progress doesn't persist," never a crash.
- `DECO_NODES` (`#ball-d1`..`d4`) are 4 pure-decoration ring icons baked into the skull artwork — clicking one replays the green clear-draw animation, plays a one-shot discovery chime (`EE.wav` via `#deco-audio`), and updates no briefing or counter. That chime is deliberately *not* routed through `duckAmbientFor()` the way puzzle clips are: it's a secret aside, not a puzzle beat, so ambient music keeps playing underneath it. Deliberately excluded from `NODES`/`CHAIN` and from keyboard handling (mouse-only secret, no hover affordance).
- `duckAmbientFor(mediaEl)` is the shared pattern behind "ambient music ducks under any puzzle clip or the solve chime": it wires `play`/`pause`/`ended` on a given `<audio>` to hold/release ambient via a counter (`duckedBy`, not a boolean, so overlapping clips can't release ambient early). Every puzzle audio player (`buildAudioPlayer`) and the cleared-chime element both go through it — don't gate ambient on `audioEl.paused` directly, that flag also flips during ducking and isn't a reliable read of user intent (`audioOn` is). Puzzle players are rebuilt fresh (a new `<audio>`, a fresh `duckAmbientFor` registration) on every `renderBriefing()` call, so `renderBriefing()` explicitly `.pause()`s whatever `<audio>` is still in the outgoing briefing before wiping it with `innerHTML = ""` — removing a *playing* media element from the DOM doesn't stop it (that's standard browser behavior, not a bug), and an orphaned-but-playing clip both keeps making sound and never fires the `pause`/`ended` event `duckAmbientFor` is waiting on to release its ambient duck, which is what "ambient randomly stays ducked or comes back at a weird moment" turned out to be. Any future code that swaps out a container holding a live `<audio>` needs the same explicit `.pause()` first — it's not something `duckAmbientFor` can protect against on its own, since by the time the element's gone, there's nothing left to call `.pause()` on.
- The `#reset-progress` button (console.html) + its console.js handler + `.hud-reset` CSS rules are an explicitly temporary dev/testing aid — clears `skynet:progress` and reloads. Flagged in all three files for removal before launch; don't extend it into a real feature without checking that's still wanted.

## Conventions the pages follow

- Each page's CSS lives in `styles/<page>.css`, JS in `scripts/<page>.js`, loaded via `<link rel="stylesheet">` / `<script src>` at the same point in the markup the inline block used to occupy (so load-order/timing is unchanged from when they were inline). Only shared tokens/fonts live in `theme.css`. Files start at `<title>` with no doctype/html/head/body wrappers — match that style. The one exception is the skull SVG markup in `console.html`, which stays inline (see Architecture above).
- Audio and entry animations are gated behind the first click/keypress (browser autoplay policy). Both pages use a run-once flag plus a `.play` class that the CSS animation blocks key off.
- Every animation has a `prefers-reduced-motion` story: entry/looping animations live inside `no-preference` media blocks so reduced-motion users get the final state immediately (nothing is left at `opacity: 0` waiting on an animation that never runs).
- Staggered reveals use a per-item `--i` custom property set from JS, consumed by `animation-delay: calc(var(--i) * Xms)`.
- Colors always come from the theme tokens: `--signal` (red) is the accent/danger color, `--cleared` the green for done states.
